Interaction model
ActionBehavior
Tap row body Expand / collapse children. If leaf node (no children), toggle selection instead.
Tap checkbox Toggle selection. Selecting a parent selects all descendants recursively. Deselecting a parent deselects all.
Partial state ◐ Parent shows partial when some (not all) descendants are selected. Tapping partial → selects all.
Chevron › Present on any row with children. Rotates 90° when expanded. Click anywhere on row to toggle.
Indent lines Vertical connector lines at each depth level show hierarchy. Depth 1 = 28px indent, depth 2 = 48px, depth 3 = 68px.
Size bars Proportional within each level — children's bars are relative to sibling max, not global max.
Size rollup Parent shows total of all descendants. "You can free ~X GB" counts only selected items at leaf level (no double-counting).
Grouping rules — what becomes a parent
1

Top-level groups by scan source path. Items from /Applications group under "Applications". Items from ~/Library/Caches group under "~/Library/Caches". Items from ~/Projects group under "~/Projects". Custom-added folders become their own top-level group.

2

App groups nest inside their scan source. "Zed" appears under "Applications" (because its bundle is at /Applications/Zed.app). Its children (bundle, cache, support) appear as depth-2 items under Zed.

3

Folder items with shared parents auto-group. If ~/Projects/A/node_modules and ~/Projects/B/node_modules both appear, they nest under ~/Projects → A and B as intermediate groups.

4

Leaf nodes = no children. An item with no sub-items (e.g., a single cache folder) is a leaf. Tapping a leaf toggles selection directly — no expand/collapse.

5

Default state: top-level collapsed. User sees top-level groups (Applications, ~/Projects, ~/Library/Caches, Dev Tools) with total sizes. Drill down to find what's big inside each.

Data flow — how items become a tree
scan() → appGroups + looseItems (existing, unchanged)
    │
    ▼
buildTree() → group by scan source path
    │
    ├── /Applications
    │   ├── League of Legends  (leaf — single bundle)
    │   ├── Docker             (expandable — bundle + cache + support)
    │   │   ├── App Bundle
    │   │   ├── App Cache
    │   │   └── App Support

    ├── ~/Library/Caches

Open design decisions
?

Max depth limit? Should we cap at depth 3 (parent → child → grandchild) to avoid endlessly deep trees? Or allow unlimited drill-down for custom folders?

?

Auto-expand single children? If "~/Projects" has only one child "OscarProjects", should it auto-expand to avoid a useless click? Or keep everything collapsed by default for consistency?

?

Filter chips with hierarchy? When "Apps" filter is active, show only app-related branches (Applications → app groups), hiding Caches and Projects? Or flatten back to the current flat list behavior for filters?
